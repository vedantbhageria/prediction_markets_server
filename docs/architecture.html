Architecture · kept up to date

Prediction markets server

A 24/7 Ubuntu machine that keeps every Kalshi market from the last 30 days, with one-minute trade candles, a viewer and an API.

~185,000Kalshi markets open right now
2.87 millionmarkets stored (open + closed in 30 days)
1 minutecandle size, rolled up to 5m · 15m · 1h
240 / minKalshi requests, shared by every program

1The big picture

Kalshi in, four programs, one database, two ways to look at it.

2The machine and how you reach it

One PC on the office network, reachable only through your own devices.

Ubuntu Server LTS

8 cores, 44 GB RAM, 500 GB NVMe; RAM tested, idle power-saving off.

Tailscale

Private network between server, laptop and iPad — server is 100.106.150.105.

SSH with keys

Laptop and iPad (Termius) log in with keys, no password needed.

Encrypted DNS

Cloudflare DNS over TLS, because the office network refuses normal lookups.

Public viewer link waiting

Tailscale Funnel is on; its certificate needs the server to reach Let's Encrypt.

Git deploy

Push from the laptop to the server's bare repo and the code updates itself.

3The programs

Each one starts, stops and restarts on its own — none waits for another.

discover.py every 15 min

Lists every open market, imports newly closed ones, deletes those over 30 days old.

activity.py after each scan

Turns each scan's volumes into busy-ness scores and picks the hot list (~3 s).

live.py every minute

Fetches new candles for hot markets, then for any market that traded since.

backfill.py by hand

Fills old history, reports coverage, checks candles against volumes, repairs.

viewer.py always on

The browser viewer, same look as before, behind a username and password.

api/ backbone

FastAPI on uvicorn; only /health for now, endpoints come later.

4Where the data lives

Every fact in one table, each linked to the one above it.

TableWhat it holds
kalshi_marketsEvery market open now or closed in the last 30 days, exactly as Kalshi sends it.
kalshi_candlesOne row per market per minute with a trade; quiet minutes are filled in when read.
kalshi_trackingPer market: last volume, when it was read, activity score, and which minutes are fetched.
kalshi_scansOne row per discovery scan, so activity.py scores each exactly once.
kalshi_observationsHand-off from discover to activity: each market's volume and when it was true.
*_5m / *_15m / *_1hTimescaleDB rollups that refresh themselves and include the newest minutes.

5How live candles work

Spend requests only where trades are happening.

new market score = total volume ÷ minutes since it opened
every scan rate = Δvolume ÷ Δminutes
score = score + (1 − 2−Δminutes/60) × (rate − score) ← one-hour half-life

Trades only

Minutes with quotes but no trade are dropped; nothing is invented.

Late trades caught

A minute is read 60 s after it ends; hot markets re-read the last 2 minutes.

No-change proof

Each reading keeps its ask and answer times, so "unchanged" can never hide a trade.

History

backfill.py goes newest-first back to the open (or 30 days); never-traded markets cost nothing.

6Staying inside Kalshi's limit

One bucket of request tokens in Redis; every program draws from it.

Hard ceiling

No 60-second window can ever exceed the budget, however many programs run.

Hot cap

Hot list size = 100 × (budget − headroom − discovery − warm), recomputed every scan.

Batch candles

Up to 100 markets and 10,000 market-minutes per request, packed automatically.

7When things go wrong

Everything is saved as it arrives, and the bookkeeping only moves once data is written, so nothing is lost or fetched twice.

What happensWhat the system does
A program crashesRestarts and carries on from the bookkeeping; nothing lost, nothing doubled.
Network drops outEvery request pauses; one check every 30 s; all carry on from where they were as soon as it is back.
Kalshi throttlesBudget halves for everyone at once, then recovers slowly.
Discovery stops mid-scanSaves its place after every page and finishes the same scan from there.
activity.py is downScans wait in order and are scored one by one when it returns.
Redis is downEach program falls back to a third of the budget; live works out the hot list itself.
Server off for daysDiscovery re-imports the closed markets; live catches up; backfill fills the rest.

8Tested

Against a simulated Kalshi with known trades, so every candle can be checked exactly.

  • Activity rules, case by case11 cases: new, closed, quiet chains, late coverage, averages, odd readings — all pass.
  • Shared budget under three processesBusiest 60 s held exactly 120 of 120; after a 429 the rate halved; hot always went first.
  • Database upgradeOld layout with filled upgraded in place; candles kept; rollups rebuilt.
  • 30-minute end-to-end run with faultsCrashes, a network drop, 429s, Redis loss, a half scan and slow answers: 57,303 traded minutes all exactly right — 0 missing, 0 wrong, 0 extra; budget held; busiest markets all hot.
  • Real Kalshi13 settled markets: candle volumes add up exactly to Kalshi's own volume; 7,709 quote-only minutes dropped.

10Decisions we made

The short reason behind each choice.

DecisionWhy
1-minute candlesKalshi's own resolution; 5-second polling broke the rate limit.
Only traded minutesStoring empty minutes would cost ~260 million rows a day for nothing.
30-day windowMarkets open now or closed in the last 30 days; older ones are deleted.
Venue data onlyColumns for derived data exist but stay empty until we fill them.
No copied columnsA market's category and series are read from its event, not duplicated.
Scores in PostgreSQLOne statement scores 185k markets in about 3 s — no need for Rust or C++.
Separate programsEach can be stopped, restarted or rerun as a data fixer on its own.
REST, not WebSocketThe WebSocket needs an API key; REST with a budget covers it for now.
No Redis bufferPostgreSQL is on the same machine; outages are to Kalshi, so there is nothing to buffer.
