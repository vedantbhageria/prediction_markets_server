3The programs

Each one starts, stops and restarts on its own — none waits for another.

discover.py every 15 min

Lists every open market, imports newly closed ones, deletes those over 30 days old.

activity.py after each scan

Turns each scan's volumes into busy-ness scores and picks the hot list (~3 s).

live.py every minute

Fetches new candles for hot markets, then for any market that traded since.

backfill.py running

Fills old history on leftover budget, reports coverage, checks candles against volumes, repairs.

viewer.py always on

The browser viewer behind a login, with related-wording and nearby-market panels; /status charts API use, the budget and the backfill.

api/ always on

The data API for Python: markets, candles, and backfill on demand — see the API tab.

4Where the data lives

Every fact in one table, each linked to the one above it.

TableWhat it holds

kalshi_candlesOne row per market per minute with a trade; quiet minutes are filled in when read.
kalshi_trackingPer market: last volume, when it was read, activity score, and which minutes are fetched.

kalshi_observationsHand-off from discover to activity: each market's volume and when it was true.
kalshi_titlesEach distinct market title once (572k for 2.9M markets), for the related-wording search.
*_5m / *_15m / *_1hTimescaleDB rollups that refresh themselves and include the newest minutes.

5How live candles work

Spend requests only where trades are happening.

new market score = total volume ÷ minutes since it opened
every scan rate = Δvolume ÷ Δminutes
score = score + (1 − 2−Δminutes/60) × (rate − score) ← one-hour half-life

Trades only

Minutes with quotes but no trade are dropped; nothing is invented.

Late trades caught

A minute is read 60 s after it ends; hot markets re-read the last 2 minutes.

No-change proof

Each reading keeps its ask and answer times, so "unchanged" can never hide a trade.

History

backfill.py goes newest-first back to the open (or 30 days); never-traded markets cost nothing.

6Staying inside Kalshi's limit

One bucket of request tokens in Redis; every program draws from it.

Hard ceiling

No 60-second window can ever exceed the budget, however many programs run.

Hot cap

Hot list size = 100 × (budget − headroom − discovery − warm), recomputed every scan.

Batch candles

Up to 100 markets and 10,000 market-minutes per request, packed automatically.

7When things go wrong

Everything is saved as it arrives, and the bookkeeping only moves once data is written, so nothing is lost or fetched twice.

What happensWhat the system does
A program crashesRestarts and carries on from the bookkeeping; nothing lost, nothing doubled.
Network drops outEvery request pauses; one check every 30 s; all carry on from where they were as soon as it is back.
Network refuses new connectionsPrograms keep working on connections already open, so don't restart them until it lifts.
Two writers on the same rowsEvery writer locks bookkeeping rows in ticker order, so they queue instead of deadlocking.
Kalshi throttlesBudget halves for everyone at once, then recovers slowly.
Discovery stops mid-scanSaves its place after every page and finishes the same scan from there.
activity.py is downScans wait in order and are scored one by one when it returns.
Redis is downEach program falls back to a third of the budget; live works out the hot list itself.
Server off for daysDiscovery re-imports the closed markets; live catches up; backfill fills the rest.

10Decisions we made

The short reason behind each choice.

DecisionWhy
1-minute candlesKalshi's own resolution; 5-second polling broke the rate limit.
Only traded minutesStoring empty minutes would cost ~260 million rows a day for nothing.
30-day windowMarkets open now or closed in the last 30 days; older ones are deleted.
Venue data onlyColumns for derived data exist but stay empty until we fill them.
No copied columnsA market's category and series are read from its event, not duplicated.
Scores in PostgreSQLOne statement scores 185k markets in about 3 s — no need for Rust or C++.
Separate programsEach can be stopped, restarted or rerun as a data fixer on its own.
REST, not WebSocketThe WebSocket needs an API key; REST with a budget covers it for now.
No Redis bufferPostgreSQL is on the same machine; outages are to Kalshi, so there is nothing to buffer.
API shaped like AlpacaClean request shape, Binance's interval names, Zerodha's files: everything loads into pandas.
Fill when readForward fill is worked out per request, so storage stays traded minutes only.
Intervals from 1-minute rowsAlways matches what is stored, even right after a backfill; the rollups can lag 30 min.
Nearby: expiry and odds onlyA strike depends on how a title is worded; expiry and price do not.
Prices worked out when readNewest candle if newer than the listing, else the listing's last price — nothing extra stored.
API as 4 processesOne Python process tops out near 40 requests a second; four reach about 100.
Jobs held by a leaseA running backfill job has a heartbeat; any API process takes over one whose heartbeat stops.
Pushed backfills batchedUp to 100 queued jobs share each Kalshi request: 1,055 jobs took 146 requests.
Per-second cap on the budgetKalshi counts per second; at most 15 a second, so raising the budget can't trip it.
Usage history in plain filesOne JSON line a minute (~100 bytes) in data/state/monitor/, apart from the database.
Related wording over distinct titlesNearest titles first, then each one's busiest market: 0.5 s instead of 6 s.

2How a request travels

Reads come straight from the database; a backfill goes to Kalshi through the shared budget.

4Candles

Forward fill by default — but only where we know nothing traded.

ParameterMeaning
interval1m 5m 15m 1h 4h 1d — Binance's names; buckets start on round UTC times.
start · end2026-10-31, 2026-10-31T14:00:00Z or Unix seconds; end not included. Default: the last day of the market's life.
fillforward (default) or raw.
limitUp to 10,000 rows a page; follow next_page_token for the rest (pmapi does it for you).
columnsts open high low close volume open_interest filled — ts is the bucket's start, in UTC.
coverage{"from", "to", "complete"}: what is held, and whether it covers your window.

Carried in

A window that starts mid-life opens with the last close before it.

Never invented

Minutes not downloaded yet get no row; complete turns false instead.

Always current

Every interval is built from the stored minutes at the moment you ask.

5The push command

Ask the server to fetch one market again — it answers at once and works in the background.

# ask
POST /v1/backfill
{"ticker": "KXBTCD-…",
 "from": "2026-10-31", "to": "2026-11-01"}   ← optional

# answer: 202 Accepted
{"job_id": 17, "status": "queued", …}

# follow
GET /v1/backfill/17
{"status": "done", "candles": 1212,
 "progress": {"requests_done": 5, "requests_total": 5}}
  • Default stretchThe market's whole life in the store window: from its open, or 30 days back.
  • OverwritesStored candles in that stretch are replaced with Kalshi's answer.
  • Shared budgetRuns at warm priority: after hot markets, before backfill.py.
  • Survives restartsJobs are saved; one cut short is run again when the API returns.
  • One at a timeA second push for the same market while one runs gets 409.

6Formats and pandas

Add format= to any list. pmapi uses parquet on its own when pyarrow is installed.

json default

Rows plus coverage and next_page_token: pd.DataFrame(r.json()["candles"]).

csv

Straight into pd.read_csv(url, storage_options={"X-API-Key": key}).

parquet fastest

~10× smaller, real time and number types: pd.read_parquet(io.BytesIO(r.content)).

csv and parquet the next page's token is in the X-Next-Page-Token header
one market coverage is in X-Coverage-From · -To · -Complete

7Limits and errors

Every error has the same shape: {"error": {"code": "…", "message": "…"}}.

StatusCode · when
400invalid_parameter · a bad interval, time, sort or limit
401missing_key / invalid_key · no key, wrong or revoked
403read_only_key · a read key asked for a backfill
404not_found · not in the store (30-day window)
409already_queued · that market's backfill is running
429rate_limited · wait Retry-After seconds
503query_timeout / database_unavailable

600 requests a minute per key

X-RateLimit-Remaining on every answer; pmapi waits out a 429 itself.

10 backfills a minute per key

Each one costs Kalshi requests, so they are capped on their own.

Keys stored hashed

A stolen table opens nothing; a revoked key stops within a minute.

No way through to Kalshi

Only backfill jobs reach it, on their own line of the shared budget.
