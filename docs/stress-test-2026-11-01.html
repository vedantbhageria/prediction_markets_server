Stress test · 1 Nov 2026 · prediction_markets_server

The server holds up; seven things needed fixing, all fixed

Every part was pushed well past normal use on the server itself, against a simulated Kalshi and test copies of the data. Nothing fell over and nothing was lost. The run, and the production logs read alongside it, found two live bugs, two bottlenecks and three smaller faults; each is fixed and measured again below.

What broke, and how it was fixed

Ordered by how much it mattered. "After" is the same test run again on the fixed code.

high

Deadlocks in production

Found
live.py's candle writes deadlocked 6 times and activity.py's scoring 7 times in the production logs: several programs updated the same bookkeeping rows in different orders. Nothing was lost (each retries), but a failed scoring throws away 20 s of work.
Fix
Every writer of kalshi_tracking now locks its rows in ticker order first, and candles are written sorted, so two writers can only queue, never deadlock.
After
8 writers and the scorer racing on the same 2,000 markets for a minute: 3,142 writes and 121 scorings, no errors.
high

Old markets were no longer being deleted

Found
Discovery's prune failed on 4 passes in a row: candles older than 2 days are compressed, and deleting a closed market's candles needs more decompression than TimescaleDB allows by default.
Fix
Prune and candle writes lift that limit for their own transaction. Backfills writing into compressed days were heading for the same failure, and are covered too.
After
Prune of 150 markets in compressed chunks: 214,905 candles, done in 127.2 s. A 100-market backfill write into a compressed day: 144,000 rows in 9.3 s.
high

The API topped out near 40 requests a second

Found
One Python process did all the work. More clients only queued: at 100 clients the slowest 5% waited 4.5 s, while the 8-core machine sat mostly idle.
Fix
The API now runs as 4 processes. Backfill jobs are held by a renewable lease instead of being re-queued on start, so any process can take over a job whose process died.
After
92 requests a second at 20 clients (was 40); slowest 5% at 100 clients 1.8 s (was 4.5 s). 0 errors across the whole ramp.
medium

One Kalshi request per pushed backfill

Found
Pushing 1,055 backfills used 1,056 Kalshi requests and took 227 s, though one request can carry 100 markets.
Fix
A worker takes up to 100 queued jobs at once and plans them together, so they share requests. Each job still reports its own candles.
After
1,055 backfills in 146 requests, all done in 17 s; 25 spot-checked against the true trades, 0 wrong.
medium

Bursts past Kalshi's per-second limit

Found
At a budget of 1,200 a minute the bucket allowed bursts of up to 22 requests in a second; the simulated Kalshi (20 a second, like the real one) answered 4 with 429, and every 429 halves everyone's budget. Harmless at today's 240 a minute.
Fix
The budget now also caps any one second (KALSHI_MAX_PER_SECOND, 15). At 240 a minute nothing changes; raising the budget can no longer trip Kalshi's per-second limit.
After
Same 10× collector run: busiest second 15, 0 429s.
low

Viewer pages crashed on the API's own tables

Found
Opening api_requests in the table browser failed: the page assumed every table has a market column. Seen 4 times in the viewer log.
Fix
The API's tables are hidden from the table browser, and a table without a market column is ordered by its first column instead.
After
Every viewer page in the run answered; the panel and usage tests pass.
low

Processes starting together raced on the schema check

Found
Each program checks the schema when it starts. Several API processes starting at once would run those checks at the same moment and could trip over each other.
Fix
The check now takes a database lock, so programs starting together take turns.
After
4 API processes started cleanly throughout the run.

What held up

Measured on the fixed code.

  • Every read is quick on 7.8 million candlesA day of minutes 0.04 s; a month of minutes 1.5 s as JSON, 0.9 s as parquet; 100 markets of one-minute candles for a day (144k rows) 3 s.
  • No errors under load1 to 100 concurrent clients, 0 failed requests.
  • Limits are exactA key allowed 100 a minute got exactly 100 of 27,448; a flood of 26,445 bad-key requests never touched a good key (1250 of 1250 answered).
  • Database connections cut mid-loadOnly requests in flight at that instant failed (12 in the API, 4 in the viewer); everything after recovered at once, and pmapi retries those by itself.
  • Redis killed for ten seconds0 errors in 956 requests while it was down.
  • Nothing lost from the usage log72,201 API requests sent, 72,201 recorded, through both faults.
  • Collectors at ten times the sizeDiscovery read 10,750 markets in 48 s, scoring took 0.6 s, each live cycle a few seconds of its minute, and the backfill of every market finished in 2.0 minutes.
  • Production never noticedThe real live collection stayed 2–3 minutes behind, as normal, through every phase; its one slow cycle (92 s) was a network drop at that moment.

Still to decide

Not bugs; choices, and one problem outside the code.

The office network

The biggest risk by far, and not something code can fix. While this ran, the network refused new connections to Kalshi and DNS several times. Live keeps going on connections it already has, so restarting it during a block pauses it until the block lifts (it did, deploying these fixes). A 4G/5G router or a registered connection would end it.

Prune is slow on compressed days

Deleting 150 closed markets' 214,905 compressed candles took 127.2 s. Fine at today's pace, a few minutes in each 15-minute pass at worst; worth revisiting if the store grows much larger.

The viewer serves about 13 pages a second

Plenty for two people. If more people use it, run it under a production web server with several processes, as the API now is.

The Kalshi budget is the limit, not the server

At ten times the markets and five times the budget, every program kept up with time to spare. Raising KALSHI_REQUESTS_PER_MIN would shorten the backfill roughly in proportion, if Kalshi accepts it from an anonymous client; worth trying in steps, watching for 429s on the usage page.

Database connections

Peak use stayed under 20 of PostgreSQL's 100. 4 API processes can hold up to 32; add processes only with that in mind.

How it was tested

  • On the server itself (8 cores, 44 GB), so the numbers are the real machine's.
  • Everything in throwaway schemas and its own Redis; the real data and the real Kalshi were never touched. The real live collection was watched throughout.
  • Kalshi simulated, with trades known in advance, so every stored candle could be checked; it refuses more than 20 requests a second, like the real one.
  • Phases: data at scale, reads, load from 1 to 100 clients, key limits, a backfill-push storm, viewer load, database connections cut and Redis killed under load, collectors at 10× size, and the writers that failed in production racing each other.
  • The script is tests/stress_test.py; run it again any time with .venv/bin/python tests/stress_test.py.
