Polymarket build and market matching

Polymarket is now collected the way Kalshi is, through the same API, and passed a full end-to-end test against a simulated venue. Nothing is deployed yet. The second half designs title matching across both venues, with real measurements of what each venue gives and what has to be read out of the wording.

1. What was built

Polymarket has no candle endpoint, so candles are made here from its trades, which it publishes one by one with size, price and the taker's wallet. Kalshi is unchanged apart from sharing the code paths below.

PieceKalshiPolymarket
Listing marketsdiscover.py, every 15 min (unchanged)discover.py, in its own thread beside Kalshi; records each market's total and 24-hour volume
Live datalive.py: one-minute candles from Kalshi, hot markets every minutetrades.py (new): reads the feed of every Polymarket trade every 15 s; after a gap, catches up market by market

APIOne API. A Polymarket market is its condition id (0x…) wherever a ticker goes; lists take venue=kalshi|poly|all; new /v1/markets/{condition_id}/trades; Polymarket in /v1/status; push backfills work for both. pmapi.py gains pm.trades().
ViewerStatus page gains a Polymarket section: reachability and route, feed lag, trades in the last 5 min, markets to catch up, candles waiting, history progress, requests.

Two facts measured on the real Polymarket shaped this: its trade lists are served by copies running 2–6 minutes behind, each by a different amount, so coverage is claimed from the newest trade actually returned rather than the clock (Polymarket candles arrive about 5 minutes late; Kalshi's 1–2); and its listed total volume can be badly stale, so "did it trade?" uses total and 24-hour volume together.

4. Title matching: the design

Turn every market on both venues into the same record — what is asked, about whom, compared how, against what number, by when — then match records. A text embedding finds candidates; the structured fields decide the relation. Comparators and numbers stay out of the vector because embeddings cannot tell "above $70k" from "below $70k" (they score about 0.98 alike).

NormaliseEach market into one record: native fields first, regex second, a small language model for what is left.
MaskNumbers, dates and comparators replaced by slots: "Bitcoin price at ⟨time⟩ ⟨cmp⟩ ⟨x⟩".
EmbedThe masked event text, once per distinct template, with an off-the-shelf model; vectors in pgvector.
CandidatesNearest vectors across both venues, inside a compatible date window and topic.
ClassifyRules on the fields label each pair; the model only checks pairs the rules cannot settle.

Two records, same shape

// Kalshi (illustrative) — almost all native
{ venue: "kalshi",
  title: "BNB price on Dec 31, 2026?",
  yes_sub_title: "$1,400 or above",
  kind: "threshold",          // strike_type
  comparator: "greater",      // strike_type
  low: 1400, unit: "USD",     // floor_strike; unit by regex
  subject: "BNB", metric: "price",   // regex (series)
  when: "2026-12-31", when_kind: "on",
  resolution_source: "CF Benchmarks" }
// Polymarket (a real question) — read from the wording
{ venue: "poly",
  question: "Will BNB reach $1400 by December 31, 2026?",
  groupItemTitle: "↑ 1400",
  kind: "threshold",          // regex
  comparator: "greater",      // "reach"
  low: 1400, unit: "USD",     // regex + normaliser
  subject: "BNB", metric: "price",   // regex
  when: "2026-12-31", when_kind: "by",
  resolution_source: "Binance" }

These two are not the same bet: one asks whether BNB is above $1,400 on 31 December, the other whether it reaches $1,400 at any point by then, on a different price source. The matcher labels them related, not identical — the kind of difference a title-only match would miss.

5. Where a language model and embeddings are used, and why

ToolUsed forWhyWhy not more
Native fieldsEverything a venue already sendsExact and free. Kalshi covers comparator, numbers, entity and date for most markets—
RegexPolymarket's wording; Kalshi's units and subjectsTitles are formulaic: on 84,570 real Polymarket questions, regex filled every field for 98.5%. Fast, auditable, deterministicSome readings are wrong (below); each shape is checked by hand before it is trusted
Small language modelOnly questions regex cannot read, and only to fill the same fields; checking pairs the rules leave unsettledHandles irregular wording ("Saturn FDV above $400M one day after launch")Slower, and can be confidently wrong; kept to a few percent and every output marked model
EmbeddingsFinding "same event" candidates across wording ("BTC" ↔ "Bitcoin", "Fed cuts" ↔ "FOMC lowers")Cosine similarity on meaning, where trigram matching sees only shared lettersBlind to numbers, negation and comparators, so they never decide a match on their own
Training our own modelNot at firstOff-the-shelf models (bge-small, MiniLM; 384 dimensions) run on the server's CPUWorth fine-tuning only once a few thousand confirmed matches exist to learn from

Filled is not the same as right. A hand check of 70 random distinct shapes found about one in eight read wrongly, all fixable rules: "$200 by Dec 31" read as $200 billion; "2026-27 season" read as a range; "300-400k" read as 300 to 400,000; a date ladder's date taken as the entity; placeholder outcomes ("Will E win…", "Person AN") read as names; and threshold questions missing their subject. The first job of the build is fixing these and measuring accuracy on 200 hand-labelled markets per venue.

What it needs

  • pgvector installed in PostgreSQL: one sudo command from you.
  • About 770,000 distinct titles (570,000 Kalshi, 200,000 Polymarket); far fewer once numbers are masked. First embedding pass well under an hour on the CPU, then only new titles.
  • Roughly 0.5–1 GB for vectors and the HNSW index.
  • New tables propositions and matches; an API endpoint /v1/markets/{ticker}/matches; a viewer panel.

6. Decisions for you

  1. Deploy Polymarket? Restarts discover, backfill, the API and viewer once the network is quiet, adds trades.py and aggregate.py, and sets VPN_PROXY in .env. The service install (8 programs now) is still your one sudo command.
  2. Build matching? In the order above: fix and measure the extractor, then embeddings (needs pgvector), then the matcher and its labels, checked by hand on 200 pairs before use.
